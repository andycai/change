# Change 统一帧预算治理设计（MVP）

- 日期：2026-04-26
- 目标目录：`UnityProject/Assets/Change/Runtime/`
- 适用层级：Runtime（依赖 Unity 生命周期与 UniTask）
- 关联主题：Unity 日常开发中单帧 CPU 逻辑峰值治理

## 1. 背景与问题

在 Unity 日常开发中，`Update/LateUpdate/FixedUpdate` 内常出现单帧逻辑峰值，表现为：

1. 主线程阶段瞬时超时导致卡顿。
2. 业务代码接入方式不一致，难以持续治理。
3. 问题修复依赖人工经验，缺少统一预算与自动降峰机制。

本设计聚焦 CPU 逻辑峰值（非渲染、非加载、非 GC 专项），建立可复用的统一机制与团队标准。

## 2. 目标与边界

### 2.1 第一阶段目标（硬目标）

1. 在目标设备和目标场景下，`Update + LateUpdate + FixedUpdate` 合计逻辑耗时 `P95 < 4ms`。
2. 采用低侵入方式接入，不强制重构既有业务结构。
3. 允许非关键逻辑自动延后 1~3 帧以换取峰值稳定。
4. 接入 UniTask 做协作式让帧，降低长任务的单帧尖峰。

### 2.2 非目标（MVP 不做）

1. 不重构为全量自定义 PlayerLoop 框架。
2. 不覆盖渲染瓶颈、资源 IO 瓶颈和 GC 专项治理。
3. 不引入多线程 `Task.Run` 业务执行模型。

## 3. 方案比较与结论

### 3.1 方案 A：规范+人工治理

- 做法：仅新增性能规范与排查清单。
- 优点：接入最快，风险最低。
- 缺点：治理不可持续，目标达成高度依赖人工执行。

### 3.2 方案 B：轻量帧预算治理层（推荐）

- 做法：保留现有 `MonoBehaviour` 代码结构，在运行时增加统一预算决策和任务调度。
- 优点：改造小，收益稳定，可渐进落地。
- 缺点：需要新增少量基础设施与埋点。

### 3.3 方案 C：强管控执行框架

- 做法：所有逻辑迁移到统一循环系统。
- 优点：治理彻底。
- 缺点：改造成本高，不符合当前低侵入诉求。

### 3.4 结论

采用方案 B，先实现统一预算治理层；后续视效果决定是否演进到方案 C。

## 4. 总体架构

### 4.1 组件划分

1. `FrameBudgetDriver`
   - 负责在 `Update/LateUpdate/FixedUpdate` 三阶段采样与预算评估。
2. `FrameWorkScheduler`
   - 负责非关键任务排队、放行、延后与到期处理。
   - 队列建议复用 `Change.Framework.Collections` 的固定容量容器（例如 `RingBuffer<T>`）。
3. `FrameBudgetPolicy`
   - 负责预算参数与策略声明（阶段预算、最大延后帧、降频阈值）。
4. `FramePerfRecorder`
   - 负责性能统计（P50/P95、超预算次数、延后数、超期数）。

### 4.2 执行分层

- `Critical`：必须当帧执行，不可延后。
- `Important`：优先当帧，预算不足可延后 1 帧。
- `Deferred`：允许延后 1~3 帧。

### 4.3 放置层级

该机制放在 `Change.Runtime`，不进入 `Change.Framework`。原因：

1. 依赖 Unity 生命周期（Update/Late/Fixed）。
2. 依赖 UniTask 的 PlayerLoop 时序能力。

## 5. 统一标准（机制 + 规范）

### 5.1 任务分级标准

1. `Critical`
   - 输入采样、角色移动、战斗判定等必须即时反馈逻辑。
2. `Important`
   - 次要状态同步、可感知但非关键的 UI 更新。
3. `Deferred`
   - 统计聚合、低优先扫描、可滞后刷新。

### 5.2 接入标准（低侵入）

1. 原 `MonoBehaviour` 不强制重构。
2. 仅将“可延后工作”迁移到 `FrameWorkScheduler.Schedule(...)`。
3. 长循环任务必须加入分段执行点；超预算时让出本帧。

### 5.3 禁止项（热路径）

1. 在 `Update` 中执行大批量同步扫描且无切片点。
2. 在 `Update` 中执行同步 IO。
3. 在高频路径堆叠 LINQ、闭包和大规模字符串拼接。

## 6. 预算规则与超预算处置

### 6.1 默认预算（可配置）

- `Update`: 2.5ms
- `LateUpdate`: 1.0ms
- `FixedUpdate`: 0.5ms

总预算对应目标：三阶段合计 P95 控制在 4ms 内。

### 6.2 超预算处置顺序

1. 停止执行 `Deferred`。
2. `Important` 执行限额（例如每帧最多执行 K 个）。
3. 剩余任务延后到后续帧（最长 3 帧）。
4. 到期任务按策略强制执行或降级执行，并记告警。

### 6.3 连续超预算退化

在滑动窗口（例如 30 帧）中超预算占比超过阈值（例如 20%）时，触发降频模式：

- 部分 `Important/Deferred` 任务从每帧降为每 2~4 帧执行。

## 7. UniTask 集成策略

### 7.1 集成原则

1. 仅使用主线程 PlayerLoop 时序，不引入 `Task.Run` 路径。
2. 在长任务中使用协作式让帧，避免单帧长尾。

### 7.2 推荐能力

提供统一 helper（示意命名）：

- `YieldIfBudgetExceeded(PlayerLoopTiming timing, CancellationToken ct)`

典型行为：

1. 每处理 N 个元素检查当前阶段剩余预算。
2. 预算不足则 `await UniTask.Yield(timing, ct)`，在后续帧继续。

## 8. 运行时数据流

1. 阶段开始采样：记录阶段开始时间。
2. 阶段执行：`Critical` 直通，其他级别由调度器放行。
3. 阶段收尾：计算剩余预算，更新延后与限流策略。
4. 帧末记录：写入统计窗口，输出 P50/P95 与告警计数。

## 9. 错误处理与可观测性

### 9.1 Fail-fast

配置非法时启动即抛错：

- 阶段预算 <= 0
- `maxDeferralFrames < 1`
- 队列容量非法

### 9.2 任务异常处理

单任务异常记录上下文（阶段、任务标签、优先级）并隔离，不中断整个调度器。

### 9.3 观测指标

1. 三阶段耗时（P50/P95/P99）
2. 超预算次数
3. 延后任务数
4. 超期任务数
5. 降频模式触发次数

## 10. 验收与测试

### 10.1 验收标准

1. 目标场景下三阶段合计逻辑耗时 `P95 < 4ms`。
2. 连续运行 10 分钟时，逻辑尖峰频次显著下降。
3. 调度器平均开销建议 `< 0.2ms`。
4. `Critical` 逻辑无功能回归。

### 10.2 测试策略

1. 功能测试：分级、延后上限、到期策略正确。
2. 稳定性测试：高负载下无无限积压。
3. 性能测试：固定回放场景采样 5~10 分钟并输出统计。
4. 回归测试：关键路径行为一致。

## 11. 落地节奏

1. 阶段 1：接入 2~3 个已知重逻辑点进行试点。
2. 阶段 2：迁移常见批处理/扫描/统计任务。
3. 阶段 3：将“分级声明 + 延后策略 + 验证数据”纳入 PR 标准。

## 12. 风险与控制

1. 风险：任务被延后后可能引发轻微时序变化。
   - 控制：关键逻辑固定为 `Critical`，并设置最大延后帧上限。
2. 风险：调度器本身开销反噬收益。
   - 控制：采用轻量结构与固定容量队列，严格监控调度器自耗时。
3. 风险：团队接入不一致导致标准失效。
   - 控制：提供接入模板与 PR 检查项，逐步推进存量改造。

## 13. 结论

本设计以低侵入方式建立统一帧预算治理机制，优先解决 CPU 逻辑峰值造成的卡顿问题。通过“分级执行 + 预算决策 + 自动延后 + UniTask 协作让帧”，在不重构业务架构的前提下达成 `P95 < 4ms` 的第一阶段目标，并为后续更强治理方案提供演进基础。
