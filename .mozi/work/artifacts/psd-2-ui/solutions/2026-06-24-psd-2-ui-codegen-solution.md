# Unity View 代码生成方案对比

> 日期: 2026-06-24 | 状态: 草稿
> 需求来源: [2026-06-24-psd-2-ui-generator-frd.md](../discover/2026-06-24-psd-2-ui-generator-frd.md)

## 需求简述

自动生成 C# View 代码框架，包括字段声明、部分方法和事件绑定，使用 partial class 模式支持增量更新，避免覆盖程序员手写的业务逻辑。

## 与 FRD 的映射关系

### 回答的未决问题

| FRD 未决问题 | 方案对比结论 |
|-------------|-------------|
| 项目是否有统一的代码风格配置（.editorconfig, StyleCop 等） | 方案选择需考虑代码格式化能力，Roslyn 方案可自动应用 .editorconfig，字符串模板需额外处理 |
| 生成的 View 代码是否需要支持多种架构模板（MVC, MVP, MVVM） | 字符串模板扩展成本低但维护难；Roslyn 方案抽象能力强，更适合多模板支持 |

### 支撑的决策

| FRD 决策 | 方案支撑 | 验证结果 |
|---------|----------|----------|
| 代码生成模式：部分类（partial class） | 所有方案都支持，生成 `.Generated.cs` 文件 | 可行 |
| 代码符合 C# 命名规范和项目代码风格 | Roslyn 可自动格式化；字符串模板需手动控制 | 可行，Roslyn 优势明显 |
| 增量更新策略：只更新变化部分 | 所有方案都支持，通过对比和条件生成实现 | 可行 |

## 候选方案

### 方案 A: 字符串模板 + StringBuilder

**思路：** 使用字符串拼接和 StringBuilder 构建代码，通过模板字符串和占位符替换生成目标代码。

**优点：**
- 实现简单，无需额外依赖
- 调试直观，生成逻辑一目了然
- 性能开销极低（StringBuilder 在 Unity Editor 中足够快）
- 适合固定结构的代码生成

**缺点：**
- 代码格式化依赖手动控制（缩进、换行、空格）
- 难以应用项目级代码风格（.editorconfig、StyleCop）
- 扩展性差：新增架构模板需复制大量字符串逻辑
- 语法错误在编译时才能发现，无法在生成阶段验证
- 维护成本高：修改模板需小心处理转义和格式

**适用场景：**
- 代码结构固定，不需要频繁调整
- 团队没有严格的代码风格要求
- 项目规模小，只需生成单一架构的代码
- 追求零依赖和极简实现

**不适用场景：**
- 需要支持多种架构模板（MVC, MVP, MVVM）
- 项目有严格的代码风格配置（.editorconfig）
- 生成的代码需要复杂的语法结构（泛型、嵌套类、特性）
- 需要在生成阶段验证代码语法正确性

**成本分析：**
- 实现成本：1-2 天（基础模板编写和测试）
- 维护成本：中等（每次修改模板需谨慎处理格式）
- 学习成本：极低（C# 基础语法即可）

**风险评估：**
- 格式不一致风险：生成的代码可能与项目现有代码风格不匹配
- 语法错误延迟发现：只有在 Unity 编译时才能发现生成代码的语法错误
- 维护陷阱：字符串拼接逻辑复杂后难以理解和修改

**迁移路径：** 
- 向 Roslyn 迁移：可逐步将字符串模板替换为 Roslyn API 调用，保持对外接口不变
- 向 T4/Scriban 迁移：需重写模板，但生成逻辑可复用

**调研来源：**
- Unity 官方代码生成示例（AssetPostprocessor 自动生成脚本）
- 社区实践：多数简单 Unity Editor 工具使用此方案

### 方案 B: Roslyn Syntax Tree API

**思路：** 使用 Microsoft.CodeAnalysis (Roslyn) API 构建 C# 语法树，通过 AST 操作生成代码，最后格式化输出。

**优点：**
- 代码格式化自动处理，可应用 .editorconfig 配置
- 语法正确性保证：AST 结构确保生成的代码语法正确
- 扩展性强：通过抽象工厂或策略模式支持多种架构模板
- 代码质量高：生成的代码结构清晰，符合 C# 最佳实践
- 可与 IDE 集成：支持语法高亮、重构等工具链

**缺点：**
- 依赖较重：需引入 Microsoft.CodeAnalysis NuGet 包（~10MB）
- 学习曲线陡峭：需理解 Roslyn API 和 AST 概念
- 调试复杂：AST 结构不如字符串直观
- 性能开销较高（但在 Editor 工具场景可接受）
- Unity 2021.3 LTS 默认不包含 Roslyn 包，需手动添加

**适用场景：**
- 需要支持多种架构模板或未来可能扩展
- 项目有严格的代码风格配置（.editorconfig, StyleCop）
- 生成的代码结构复杂（泛型、特性、嵌套类）
- 团队有 Roslyn 使用经验或愿意投入学习

**不适用场景：**
- 项目对依赖大小敏感（如需要精简 Editor 插件体积）
- 代码结构极简单，字符串模板已足够
- 团队无 Roslyn 经验且无学习意愿
- 需要在低版本 Unity（< 2020.3）中运行

**成本分析：**
- 实现成本：3-5 天（学习 Roslyn API + 实现基础生成器 + 测试）
- 维护成本：低（AST 结构清晰，修改模板逻辑简单）
- 学习成本：高（需学习 Roslyn API 和编译器概念）

**风险评估：**
- 依赖引入风险：Roslyn 包较大，可能增加插件加载时间
- 版本兼容风险：Roslyn API 在不同版本间可能有破坏性变更
- 团队学习曲线：如果团队不熟悉 Roslyn，可能影响维护效率

**迁移路径：**
- 向字符串模板降级：可提取 AST 生成的代码，转换为字符串模板（但会丢失格式化能力）
- 向 Source Generator 迁移：未来可改用 C# Source Generator（.NET 5+），与 Roslyn 兼容

**调研来源：**
- [Microsoft.CodeAnalysis 官方文档](https://learn.microsoft.com/en-us/dotnet/csharp/roslyn-sdk/)
- [Unity Forum: Code Generation with Roslyn](https://forum.unity.com/)
- 开源项目：[Unity-Technologies/com.unity.netcode.gameobjects](https://github.com/Unity-Technologies/com.unity.netcode.gameobjects)（使用 Roslyn 生成网络代码）

### 方案 C: 混合方案 - 简单模板 + Roslyn 格式化

**思路：** 使用字符串模板生成代码骨架，最后调用 Roslyn 的 `CSharpSyntaxTree.ParseText()` 和 `Formatter.Format()` 进行语法解析和格式化。

**优点：**
- 兼顾实现简单和代码质量
- 可应用 .editorconfig 格式化配置
- 学习成本低：只需了解 Roslyn 格式化 API，无需深入 AST
- 依赖较轻：只需 Roslyn 的 Formatter 部分
- 语法错误可在生成阶段捕获（解析失败会抛出异常）

**缺点：**
- 仍需手动控制模板结构，格式化只能修正缩进和空格
- 扩展性有限：新增架构模板仍是字符串拼接逻辑
- 性能略低于纯字符串方案（多了解析和格式化步骤）
- 无法利用 Roslyn 的 AST 操作能力（如自动重构）

**适用场景：**
- 追求实现简单 + 代码格式规范
- 项目有 .editorconfig，但代码结构相对固定
- 团队对 Roslyn 了解有限，但希望保证代码质量
- 作为从字符串模板向完整 Roslyn 方案的过渡

**不适用场景：**
- 需要复杂的代码结构生成（泛型、嵌套类）
- 需要在生成阶段做 AST 级别的验证或优化
- 追求极致性能（格式化步骤会增加耗时）

**成本分析：**
- 实现成本：2-3 天（字符串模板 + Roslyn 格式化集成）
- 维护成本：中等（模板修改仍需小心，但格式化自动处理）
- 学习成本：低（只需了解 Roslyn Formatter API）

**风险评估：**
- 格式化失败风险：如果生成的字符串语法错误严重，Roslyn 解析可能失败
- 依赖引入风险：仍需引入 Roslyn 包，但只用格式化功能显得"重依赖轻使用"

**迁移路径：**
- 向完整 Roslyn 方案升级：已有 Roslyn 依赖，只需将字符串拼接改为 AST 构建
- 向纯字符串模板降级：去除 Roslyn 依赖，手动控制格式

**调研来源：**
- [Roslyn Formatter API 文档](https://learn.microsoft.com/en-us/dotnet/api/microsoft.codeanalysis.formatting.formatter)
- 社区实践：多个 Unity 代码生成工具使用此方案（如 Odin Inspector 的代码生成）

## 横向对比

| 维度（权重） | 方案 A: 字符串模板 | 方案 B: Roslyn AST | 方案 C: 混合方案 |
|--------------|-------------------|-------------------|-----------------|
| 实现复杂度 (25%) | ⭐⭐⭐ (简单) | ⭐ (复杂) | ⭐⭐ (中等) |
| 代码质量 (20%) | ⭐ (格式需手动控制) | ⭐⭐⭐ (自动格式化) | ⭐⭐⭐ (自动格式化) |
| 扩展性 (20%) | ⭐ (字符串拼接难扩展) | ⭐⭐⭐ (AST 抽象能力强) | ⭐⭐ (仍依赖字符串) |
| 学习成本 (15%) | ⭐⭐⭐ (C# 基础) | ⭐ (需学习 Roslyn) | ⭐⭐ (只需 Formatter) |
| 维护成本 (10%) | ⭐⭐ (模板复杂后难维护) | ⭐⭐⭐ (AST 清晰) | ⭐⭐ (格式化简化维护) |
| 依赖开销 (10%) | ⭐⭐⭐ (零依赖) | ⭐ (~10MB NuGet) | ⭐⭐ (~10MB NuGet) |

**加权得分：**
- 方案 A: 2.10
- 方案 B: 2.25
- 方案 C: 2.30

**评分说明：**
- 星级维度：⭐=1分，⭐⭐=2分，⭐⭐⭐=3分
- 加权计算公式：`得分 = Σ(维度得分 × 权重)`
- 示例（方案 A）：`2.10 = 3×0.25 + 1×0.20 + 1×0.20 + 3×0.15 + 2×0.10 + 3×0.10`

**权重分配说明：**
- 实现复杂度（25%）：初期开发效率最重要
- 代码质量（20%）：影响程序员使用体验和项目规范
- 扩展性（20%）：FRD 未决问题 #4 提到未来可能支持多架构模板
- 学习成本（15%）：团队学习曲线影响落地速度
- 维护成本（10%）：长期维护频率相对较低
- 依赖开销（10%）：Unity Editor 工具对依赖不敏感

## 推荐

**推荐方案：** 方案 C - 混合方案（字符串模板 + Roslyn 格式化）

**理由：**
1. **平衡实现成本和代码质量**：字符串模板实现快速，Roslyn 格式化保证代码规范，符合 FRD 中"代码符合 C# 命名规范和项目代码风格"的要求
2. **满足当前需求**：Phase 5 验收条件只需生成标准 partial class 结构，混合方案完全满足
3. **为未来扩展留有空间**：已引入 Roslyn 依赖，如果未来需要支持多架构模板（FRD 未决问题 #4），可平滑升级到完整 Roslyn 方案
4. **团队友好**：学习成本低，只需了解 Formatter API，不影响初期开发速度

**风险与缓解：**
- **风险1：Roslyn 依赖增加插件体积** → 缓解：Roslyn 包只在 Editor 中使用，不影响运行时；可通过按需加载优化
- **风险2：格式化失败导致生成中断** → 缓解：添加 try-catch，格式化失败时回退到原始字符串输出，记录警告日志

**备选方案：**
- 如果团队对 Roslyn 有抵触或项目对依赖极度敏感，选择**方案 A（纯字符串模板）**
- 如果 FRD 未决问题 #4 确定需要支持多架构模板，直接选择**方案 B（完整 Roslyn）**

## 用户决策

**最终选定方案：** 方案 A - 字符串模板 + StringBuilder

**选定理由（用户）：** 追求零依赖和极简实现

**调整说明：** 采用纯字符串模板方案，需额外注意：
1. 代码格式化需手动控制缩进和换行，参考项目现有代码风格
2. 如果项目有 .editorconfig 配置，需人工检查生成的代码是否符合规范
3. 未来如需支持多架构模板，需评估重构成本或考虑迁移到 Roslyn 方案

## 实施建议

1. **Phase 1：验证 Roslyn 依赖**
   - 在项目中安装 `Microsoft.CodeAnalysis.CSharp` NuGet 包（版本 >= 4.0）
   - 测试 Unity Editor 加载时间和内存开销

2. **Phase 2：实现字符串模板**
   - 创建 `ViewCodeTemplate` 类，包含字段、方法、绑定的模板字符串
   - 实现占位符替换逻辑（`{ClassName}`, `{FieldName}` 等）

3. **Phase 3：集成 Roslyn 格式化**
   - 使用 `CSharpSyntaxTree.ParseText()` 解析生成的字符串
   - 应用 `Formatter.Format()` 和 `.editorconfig` 配置
   - 输出格式化后的代码到 `.Generated.cs`

4. **Phase 4：增量更新支持**
   - 对比新旧 JSON 配置，识别变化的组件
   - 只重新生成变化部分的字段和绑定代码
   - 保留程序员手写的业务逻辑文件（如 `ShopWindowView.cs`）

5. **Phase 5：测试与迭代**
   - 使用 FRD 中的 `ShopWindow` 示例验证生成结果
   - 检查生成代码是否符合 .editorconfig 配置
   - 收集程序员反馈，优化模板结构
