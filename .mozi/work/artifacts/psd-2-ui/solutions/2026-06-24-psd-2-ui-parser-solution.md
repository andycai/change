# PSD 解析与智能分析管线 方案对比

> 日期: 2026-06-24 | 状态: 草稿
> 需求来源: `.mozi/artifacts/psd-2-ui/discover/2026-06-24-psd-2-ui-parser-frd.md`

## 需求简述

建立 Node.js 工具链，解析 PSD 文件并通过 CV 算法和 AI 识别自动分析 UI 组件属性，输出包含完整 UI 结构和语义信息的 JSON 配置文件，为后续 Unity Prefab 生成提供数据基础。

## 与 FRD 的映射关系

### 回答的未决问题

| FRD 未决问题 | 方案对比结论 |
|-------------|-------------|
| Codex/Claude Code 的具体调用方式（API、CLI、其他） | **方案 A（Claude API Vision）**：通过 `@anthropic-ai/sdk` 直接调用，支持图像分析和结构化输出。**方案 B（基于规则）**：无需 AI 调用，完全依赖标签解析和启发式规则。**方案 C（本地 CV + 轻量 AI）**：使用 OpenCV 做边界检测，仅在复杂场景调用 Claude API。推荐 **方案 C**，平衡准确率和成本。 |

## 候选方案

### 方案 A: 全流程 AI 驱动 + CV 辅助

**思路：** 优先解析标签，无标签时对每个图层组调用 Claude API Vision 识别组件类型，九宫格检测用 OpenCV 像素相似度分析，布局识别用几何规则。

**优点：**
- 对无标签图层的识别准确率高（Claude Vision 支持多模态推理）
- 泛化能力强，适应不同美术风格
- 实现相对简单，核心逻辑清晰（标签 → AI → CV）

**缺点：**
- 每次解析调用多次 Claude API，成本较高（按 token 计费）
- 依赖网络连接，离线环境不可用
- 大型 PSD（几百个图层）解析时间较长（API 调用串行）

**适用场景：**
- 美术团队不熟悉标签规范，大量图层无标签
- 需要处理多种美术风格的 PSD
- 开发环境网络稳定，预算允许 API 成本

**不适用场景：**
- 离线环境或内网环境（无法访问 Claude API）
- 成本敏感项目（大量 PSD 需频繁解析）
- 实时性要求高（API 调用延迟不可接受）

**成本分析：**
- 实现成本：2-3 天（集成 `@anthropic-ai/sdk`，编写 prompt 模板，处理结构化输出）
- 维护成本：低（API 稳定，无需维护模型）
- 学习成本：低（团队已熟悉 Claude API）
- 运行成本：中等（假设 100 图层 PSD，20 个无标签组件，每次解析约 0.5 美元）

**风险评估：**
- Claude API 限流或服务中断导致解析失败（缓解：本地缓存识别结果，支持重试）
- AI 识别错误导致后续 Unity 生成问题（缓解：低置信度标记"需审查"，支持手动修正）
- 成本随 PSD 复杂度线性增长（缓解：优先标签解析，减少 API 调用）

**迁移路径：** 
- 向方案 C 迁移容易（增加缓存层，减少 API 调用）
- 向方案 B 迁移困难（需手动补充标签或重写规则引擎）

**调研来源：**
- [Claude API Documentation - Vision](https://docs.anthropic.com/claude/docs/vision)
- [Anthropic SDK for TypeScript](https://github.com/anthropics/anthropic-sdk-typescript)

### 方案 B: 纯规则驱动（零 AI）

**思路：** 完全依赖标签解析（PSD2UGUI-LayerTagMenu.jsx 标签体系），无标签图层标记为"未识别"，九宫格检测跳过或要求手动标记，布局识别用几何启发式规则。

**优点：**
- 零 API 成本，完全离线可用
- 解析速度快（无网络 IO），可处理大型 PSD
- 实现简单，无第三方依赖（除 ag-psd、OpenCV）
- 可预测性强（规则确定，无 AI 不确定性）

**缺点：**
- 对无标签图层无识别能力（只能标记"需审查"）
- 九宫格检测准确率依赖启发式规则（复杂纹理效果差）
- 无法适应新的 UI 模式（需手动扩展规则库）
- 对美术团队标签规范依赖强（学习成本转移到美术侧）

**适用场景：**
- 美术团队已完全遵循标签规范，无标签图层极少
- 离线环境或内网环境（无法访问外部 API）
- 成本敏感项目，需严格控制运行成本
- 实时性要求高（解析速度优先）

**不适用场景：**
- 美术团队标签使用不规范（大量无标签图层）
- 需要处理历史 PSD（无标签）
- 需要识别非标准 UI 组件（规则库未覆盖）

**成本分析：**
- 实现成本：1-2 天（编写标签解析器，实现启发式规则）
- 维护成本：中等（新 UI 模式需扩展规则库）
- 学习成本：低（逻辑简单，无第三方 AI 依赖）
- 运行成本：零（无 API 调用）

**风险评估：**
- 对无标签图层完全无识别能力（缓解：强制美术遵循标签规范，提供标签检查工具）
- 启发式规则覆盖不全（缓解：建立规则库，逐步扩展）
- 美术学习标签成本转移（缓解：提供 Photoshop 脚本辅助标签）

**迁移路径：**
- 向方案 C 迁移容易（增加 AI 识别层，保留规则引擎）
- 向方案 A 迁移容易（替换规则引擎为 AI 调用）

**调研来源：**
- 现有 PSD2UGUI-LayerTagMenu.jsx 标签体系（项目内部）
- [OpenCV.js Documentation](https://docs.opencv.org/4.x/d5/d10/tutorial_js_root.html)

### 方案 C: 混合模式（标签优先 + 选择性 AI + CV）

**思路：** 三级识别策略：(1) 优先解析标签；(2) 标签缺失时，对简单组件（边界清晰、结构简单）用 CV 启发式识别；(3) 复杂组件调用 Claude API Vision；九宫格检测用 OpenCV 并缓存结果；布局识别用几何规则。

**优点：**
- 平衡准确率和成本（标签免费、CV 免费、AI 按需）
- 灵活性高，可根据项目预算调整 AI 调用阈值
- 解析速度较快（大部分组件走标签或 CV，少量 AI 调用）
- 渐进式降级策略，容错性强

**缺点：**
- 实现复杂度最高（需维护三套识别逻辑）
- CV 启发式规则需大量测试和调优
- AI 调用阈值需根据实际 PSD 数据调整（初期可能不准确）

**适用场景：**
- 美术团队部分遵循标签规范（有标签但不完整）
- 需要平衡成本和准确率
- 项目预算有限但需要一定的 AI 识别能力
- 需要处理混合场景（新 PSD 有标签，历史 PSD 无标签）

**不适用场景：**
- 极简项目（全标签或全无标签，混合策略过度设计）
- 实时性要求极高（三级策略增加判断开销）

**成本分析：**
- 实现成本：3-4 天（三套识别逻辑，阈值调优，缓存机制）
- 维护成本：中等（CV 规则需迭代，AI 调用阈值需调整）
- 学习成本：中等（理解三级策略和阈值配置）
- 运行成本：低（假设 100 图层 PSD，80% 有标签，15% 走 CV，5% 走 AI，每次解析约 0.05 美元）

**风险评估：**
- CV 启发式规则误判（缓解：低置信度组件走 AI，避免错误累积）
- 三级策略逻辑复杂，调试困难（缓解：结构化日志，记录每个组件的识别路径）
- 阈值调整依赖实际数据（缓解：提供配置文件，支持动态调整）

**迁移路径：**
- 向方案 A 迁移容易（移除 CV 层，全部走 AI）
- 向方案 B 迁移容易（移除 AI 层，全部走规则）

**调研来源：**
- [Claude API Documentation - Vision](https://docs.anthropic.com/claude/docs/vision)
- [OpenCV.js Documentation](https://docs.opencv.org/4.x/d5/d10/tutorial_js_root.html)
- [Nine-patch Detection Algorithms](https://github.com/topics/nine-patch)

## 横向对比

| 维度（权重） | 方案 A: 全流程 AI | 方案 B: 纯规则 | 方案 C: 混合模式 |
|--------------|------------------|---------------|-----------------|
| **复杂度** (20%) | ⭐⭐ (简单，核心逻辑清晰) | ⭐⭐⭐ (最简单，纯规则引擎) | ⭐ (复杂，三套逻辑) |
| **准确率** (30%) | ⭐⭐⭐ (AI 识别准确率高) | ⭐ (依赖标签，无标签无能力) | ⭐⭐ (平衡，标签+AI 覆盖) |
| **成本** (25%) | ⭐ (API 成本高，~$0.5/PSD) | ⭐⭐⭐ (零成本) | ⭐⭐⭐ (低成本，~$0.05/PSD) |
| **离线可用性** (10%) | ⭐ (依赖网络) | ⭐⭐⭐ (完全离线) | ⭐⭐ (部分离线，AI 降级) |
| **扩展性** (10%) | ⭐⭐⭐ (AI 自动适应新模式) | ⭐ (需手动扩展规则) | ⭐⭐ (CV 规则需扩展) |
| **维护性** (5%) | ⭐⭐⭐ (API 稳定，无需维护) | ⭐⭐ (规则库需维护) | ⭐⭐ (三套逻辑需维护) |

**加权得分计算：**
- **方案 A**: 2×0.2 + 3×0.3 + 1×0.25 + 1×0.1 + 3×0.1 + 3×0.05 = **2.00**
- **方案 B**: 3×0.2 + 1×0.3 + 3×0.25 + 3×0.1 + 1×0.1 + 2×0.05 = **1.95**
- **方案 C**: 1×0.2 + 2×0.3 + 3×0.25 + 2×0.1 + 2×0.1 + 2×0.05 = **2.15**

**评分说明：**
- 星级维度：⭐=1 分，⭐⭐=2 分，⭐⭐⭐=3 分
- 权重分配理由：
  - **准确率 (30%)**：核心目标，直接影响后续 Unity 生成质量
  - **成本 (25%)**：长期运行成本，需控制
  - **复杂度 (20%)**：影响开发和维护效率
  - **离线可用性 (10%)**：部分团队内网环境需求
  - **扩展性 (10%)**：未来新 UI 模式的适应能力
  - **维护性 (5%)**：长期维护负担

## 推荐

**推荐方案：方案 C（混合模式）**

**理由：**
1. **成本与准确率平衡最优**：80% 标签 + 15% CV + 5% AI 的分布下，单次解析成本仅 $0.05，远低于方案 A 的 $0.5，同时准确率显著优于方案 B。
2. **符合实际使用场景**：美术团队逐步学习标签规范的过程中，混合模式提供渐进式支持（有标签用标签，无标签用 AI）。
3. **可配置性强**：通过调整 AI 调用阈值，可在成本和准确率之间灵活权衡，适应不同项目预算。
4. **风险可控**：三级识别策略提供多层保险，单点失败不影响整体可用性。

**风险与缓解：**
- **风险 1**：CV 启发式规则初期准确率不足 → **缓解**：第一版仅覆盖简单组件（矩形、单图片），复杂组件直接走 AI；后续根据实际数据迭代规则库。
- **风险 2**：三级策略逻辑复杂，调试困难 → **缓解**：结构化日志记录每个组件的识别路径（标签/CV/AI），提供 `--debug` 模式输出详细决策树。
- **风险 3**：AI 调用阈值需根据实际数据调整 → **缓解**：提供配置文件 `psd-exporter.config.json`，支持 `aiThreshold`、`cvConfidenceMin` 等参数动态调整。

**备选方案：**
- **如果预算充足且追求最高准确率**：选择 **方案 A**（全流程 AI），牺牲成本换取识别质量。
- **如果完全离线环境或零预算约束**：选择 **方案 B**（纯规则），强制美术遵循标签规范，提供标签检查工具降低人工成本。

**实施建议：**
1. **Phase 1**：实现标签解析 + AI 识别（跳过 CV 层），快速验证端到端流程。
2. **Phase 2**：增加 OpenCV 九宫格检测和简单组件 CV 识别，降低 AI 调用频率。
3. **Phase 3**：根据实际 PSD 数据调优 AI 阈值和 CV 规则，达到成本/准确率最优平衡。
